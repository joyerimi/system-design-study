> ⚠️ 인터뷰에서는 명확한 정답이 없는 모호한 조건으로 문제 제시됨
> 
> 
> → 적절한 질문을 통해 **요구사항을 스스로 정의하는 능력**이 중요
> 
- **목표**: 하루 **1,000만 건 푸시**, **100만 건 SMS**, **500만 건 이메일**을 처리할 수 있는 **확장 가능한 알림 시스템** 설계
- **특징**
    - 지원 채널: **모바일 푸시, SMS, 이메일**
    - 전달 시간: **Soft real-time** (약간의 지연은 허용됨)
    - 지원 디바이스: **iOS, Android, PC(랩톱/데스크톱)**
    - 알림 생성 주체
        - **클라이언트 앱**
        - **서버에서 예약 발송**
    - 사용자 설정: **수신 거부(opt-out)** 가능

# 2단계: 개략적 설계안 제시 및 동의 구하기

## 2.1 알림 유형별 처리 방식

### 공통 구조

![image.png](https://github.com/user-attachments/assets/9d5dfc1e-83d4-4847-bef3-4d549b39fd0d)

모든 알림은 이 구조를 따른다.

### 알림 제공자

- 알림 요청 생성
    
    → **단말 토큰`(device token)`** + **페이로드(JSON)** 조합
    
- 제3자 서비스에 알림 전달

### 알림 유형별 처리 방식

| 알림 유형 | 제3자 서비스 |
| --- | --- |
| **iOS 푸시** | APNS (Apple Push Notification Service) |
| **Android 푸시** | FCM (Firebase Cloud Messaging) |
| **SMS** | Twilio, Nexmo 등 SMS API |
| **이메일** | SendGrid, Mailchimp 등 이메일 API |

## 2.3 개략적 설계안 (초안)

![image.png](https://github.com/user-attachments/assets/d493a1bc-8fe7-4068-9738-61b02fe54a20)

### 시스템 구성 요소

1. **서비스 1~N**
    - 알림을 요청하는 내부 시스템 (예: 과금, 배송 등)
    - REST API 등을 통해 알림 전송 요청을 보냄
2. **알림 시스템 (Notification System)**
    - 단일 서버로 구성
    - 역할
        - API 요청 수신
        - 사용자 정보 및 템플릿 조회 (DB, 캐시 직접 접근)
        - 알림 페이로드 생성
        - 제3자 서비스(Firebase, Twilio 등)에 직접 동기 전송
3. **제3자 서비스**
    - 실제로 알림을 사용자에게 전달하는 외부 서비스
    - 예: APNS(iOS), FCM(Android), Twilio(SMS), SendGrid(Email)
4. **사용자 단말**
    - 알림을 최종 수신하는 디바이스 (앱, 문자, 이메일 등)

### 설계의 문제점

1. **SPOF (Single Point of Failure)**
    - 알림 서버가 단일 인스턴스로 구성되어 있어 장애 발생 시 전체 기능 중단
2. **확장성 부족**
    - **알림 서버 하나가 모든 역할(DB, 캐시, 페이로드 생성, 외부 전송)을 담당**
    - 서버 수를 늘리더라도 내부 로직이 모두 엮여 있어
        - DB 커넥션 수 증가
        - 캐시 적중률 하락
        - 전송 로직이 병렬화되지 않음
    - 특정 기능만 분리하거나 독립적으로 확장하는 게 사실상 어려움
3. **성능 병목**
    - 알림 전송은 무거운 작업 (템플릿 생성, 외부 API 대기 등 포함)
    - 사용자 트래픽이 몰리면 알림 서버에 부하 집중 → 전체 성능 저하

## 2.4 개략적 설계안 (개선안)

![image.png](https://github.com/user-attachments/assets/a7ac2c07-fe88-4ff3-82be-1ec53828a0e1)

### 개선 방향

- 알림 서버의 역할을 단순화 → **요청 수신 및 큐 전송만 담당**
- 메시지 큐 도입 → **전송 로직을 워커로 분리**, 비동기 처리
- DB, 캐시도 별도 계층으로 분리 → **알림 서버는 상태 없는 Stateless 서버로 구성**
- 전송 병목 제거, **각 컴포넌트를 독립적으로 수평 확장 가능**

### 시스템 구성 요소

| 구성 요소 | 역할 |
| --- | --- |
| **서비스 1~N** | 알림 요청을 보내는 내부 시스템 |
| **알림 서버** | • API 수신
• 유저/단말 정보, 템플릿 조회 (DB/캐시 접근)
• 알림 이벤트 생성 → **메시지 큐에 넣고 끝** |
| **캐시** | 사용자 정보, 템플릿 등 고속 접근용 데이터 저장 |
| **데이터베이스** | 사용자 정보, 수신 설정, 알림 로그 저장 |
| **메시지 큐** | • 알림 유형별로 큐 분리 (iOS, Android, SMS, Email 등)
• 병렬 처리 및 장애 격리 가능 |
| **작업 서버 (Worker)** | • 큐에서 이벤트 꺼내 제3자 서비스로 전송
• 필요 시 재시도, 실패 처리 담당 |
| **제3자 서비스** | • 알림을 실제 사용자에게 전달
• 예: APNS, FCM, Twilio, SendGrid 등 |
| **사용자 단말** | 알림 수신 디바이스 (앱, 문자, 이메일 등) |

### 알림 전송 흐름

1. 내부 서비스가 알림 서버의 API 호출
2. 알림 서버가 DB/캐시에서 사용자 정보, 설정, 템플릿을 조회
3. 알림 페이로드 생성 후 **적절한 메시지 큐에 등록**
4. 작업 서버(worker)가 큐에서 이벤트 꺼냄
5. 제3자 서비스에 요청 전송
6. 사용자 단말에서 알림 수신

### 알림 API 예시 (SMS)

```
POST https://api.example.com/v/sms/send
```

```json
{
  "to": [{ "user_id": 123456 }],
  "from": { "email": "from_address@example.com" },
  "subject": "Hello, World!",
  "content": [
    {
      "type": "text/plain",
      "value": "Hello, World!"
    }
  ]
}
```

# 3단계: 상세 설계

## 3.1 안정성

### 3.1.1 데이터 손실 방지

![image.png](https://github.com/user-attachments/assets/2fc0f446-d0b6-4914-a320-1d058ff3567f)

- 알림 시스템에서 가장 중요한 건 **알림이 절대 사라지지 않아야 한다**는 것
- **지연**되거나 **순서가 어긋나는 건 괜찮지만**, **소실은 치명적**
- 이를 위해
    - **알림 데이터를 DB에 저장** (예: `notification_log` 테이블)
    - **재시도 메커니즘**을 구현해 실패 시 다시 시도 가능하도록 구성

### 3.1.2 중복 전송 방지

- **분산 시스템 특성상** 알림이 중복 전송될 가능성은 항상 존재
- 완벽히 막을 수는 없지만, **중복 감지 로직**으로 빈도를 줄일 수 있음
    - 예: 알림 도착 시 `event_id`를 확인해 **이미 처리한 이벤트인지 검사**
    - 중복이면 무시, 아니면 발송

> 중복 전송을 100% 방지하는 건 불가능하지만, 신중한 처리로 최소화 가능
> 

### 왜 중복을 완전히 막을 수 없는가?

- 분산 시스템에서는 **네트워크 지연**, **ACK 손실**, **프로세스 장애** 등으로 인해
    
    **발신자와 수신자가 서로의 상태를 정확히 알 수 없다**
    
- 이로 인해, 다음과 같은 상황이 발생할 수 있다.
    - 메시지를 처리했지만 ACK를 못 보냄 → 발신자는 실패로 간주하고 재전송 → **중복**
    - ACK를 받았지만 실제로는 수신자가 처리하지 못함 → **손실**
- 즉, **"정확히 한 번만 전달(Exactly-once)"**은 불가능함
    
    → 현실적으로는 **At-least-once + Idempotency** 전략을 채택함
    

## 3.2 사용자 고려사항

### 3.2.1 알림 템플릿

- 반복되는 알림 메시지를 **형식화된 틀**(template)로 관리
- 파라미터(`item_name`, `date` 등)만 바꿔 다양한 메시지 생성
- 이점: **일관성 유지**, **오류 감소**, **작성 시간 절약**

**예시**

본문: `[item_name]`이 다시 입고되었습니다! `[date]`까지만 주문 가능

제: 지금 `[item_name]`을 주문 또는 예약하세요!

### 3.2.2 수신 설정

- 사용자가 **알림 수신 여부와 채널**(Push, Email, SMS 등)을 직접 조정할 수 있도록 설정
- 설정 정보는 DB의 `알림 설정 테이블`에 저장됨

**예시 필드**:

- `user_id`: 사용자 ID
- `channel`: 알림 채널
- `opt_in`: 수신 동의 여부

> 알림 전송 전, 사용자가 해당 채널을 수신 허용했는지 반드시 확인해야 함
> 

### 3.2.3 전송률 제한

- **개별 사용자에게 일정 시간 동안 보낼 수 있는 알림 수를 제한**
- 목적: **알림 과잉으로 인한 피로감 방지**, 수신 거부(opt-out) 예방

## 3.3 전송 실패 처리

- **알림 전송 실패 시**, 알림을 **재시도 큐에 넣어 일정 횟수 재전송 시도**
- **지속적인 실패 발생 시**, **개발자에게 경고(alert)** 전송

## 3.4 인증 및 보안

- **iOS/Android 푸시 알림 API는 `appKey`와 `appSecret`을 사용해 인증**
- **인증된 클라이언트만 알림 API를 사용할 수 있도록 제한**

## 3.5 큐 모니터링

- 중요한 지표: **큐에 쌓인 알림 수**
- 수치가 높으면 **작업 서버 처리 속도가 부족하다는 신호**
- 해결 방법: **작업 서버(worker) 증설**로 처리량 확대

## 3.6 이벤트 추적

- **클릭률, 수신 여부, 수신 거부율** 등은 사용자 분석에 핵심
- 알림 시스템은 **분석 서비스와 연동**해 이벤트 흐름을 추적해야 함

![image.png](https://github.com/user-attachments/assets/be46b47b-7ba4-4cb8-94f4-2b107466a671)

→ 각 단계는 **추적 지표로 활용**됨

## 3.7 최종 설계

![image.png](https://github.com/user-attachments/assets/9b6252f7-fa13-45a0-a2d1-724dad9ae798)

1. **알림 서버 기능 강화**
    - 인증(Authentication) 추가
    - 전송률 제한(Rate Limiting) 적용
2. **신뢰성 향상**
    - 실패한 알림은 **재시도 큐에 저장** 후 재전송 시도
    - 알림 로그 DB로 **데이터 유실 방지**
3. **템플릿 도입**
    - 템플릿 기반으로 알림 생성 → **형식 일관성 유지**, 작성 간소화
4. **모니터링 & 추적**
    - 이벤트 추적 및 클릭 데이터는 **분석 서비스로 연동**
    - **시스템 상태 가시화 및 개선에 기여**

# 4단계: 마무리

이번 장에서는 **확장 가능하고, 다양한 채널을 지원하며, 결합도가 낮은 설계**를 구축하였다.

### 핵심 설계 포인트 요약

- **안정성**: 실패 시 재시도 가능한 **신뢰성 있는 전송 구조**
- **보안**: `appKey`, `appSecret` 기반의 **API 인증**
- **이벤트 추적 & 모니터링**: 각 단계별 이벤트 흐름 추적 및 시스템 상태 확인
- **사용자 설정**: 채널별 **수신 동의 여부** 확인 후 알림 전송
- **전송률 제한**: **사용자 피로도 최소화**를 위한 빈도 제한 기능 도입
