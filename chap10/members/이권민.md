# 가상 면접 사례로 배우는 대규모 시스템 설계 기초(10장 - 알림 시스템 설계)

스터디 날짜: 2025년 8월 27일

# 알림 시스템의 종류

- 모바일 푸시 알림
- SMS 메시지
- 이메일

# 요구사항

## 지연시간

- soft real-time: 가능한 한 빨리 전달되어야 함. 서버에 부하가 있을 때 약간의 지연은 무방

## 단말, 플랫폼

- iOS
- android
- 랩톱/데스크톱

## 알림 생산자

- 클랑이언트 애플리케이션
- 서버 측 스케줄링

## 알림 소비자

- 알림 수신 거부 기능 필요. opt-out

## 알림 생산량

- 천만 건의 모바일 푸시 알림
- 백만 건의 SMS
- 5백만 건의 이메일

# 개략적 설계

## 알림 유형별 지원 방안

### iOS 푸시 알림

푸시 알림을 보내기 위한 세가지 컴포넌트

- 알림 제공자: 알림 요청을 만들어 APNS로 보내는 주체
- APNS: 애플이 제공하는 원격 서비스
- iOS 단말

### 안드로이드 푸시 알림

- iOS와 비슷하지만 APNS 말고 FCM을 사용

### SMS 메시지

- 제 3 사업자의 서비스 이용
- 대부분 요금이 나옴

### 이메일

- 고유 이메일 서버 구축
- 상용 이메일 서비스 사용

## 연락처 정보 수집 절차

- 알림을 보내기 위해서는 단말 토큰, 전화번호, 이메일 주소 등의 정보가 필요
- 처음 앱을 설치하거나 계정을 등록할 때 API 서버는 사용자 정보를 수집하여 DB에 저장
- 유의할 점은 한 사용자가 여러 개의 단말을 가질 수 있고, 해당 사용자에게 알림을 보내야 한다면 연결된 모든 단말에 전송되어야 함

## 알림 전송 및 수신 절차

### 요구사항

- N개의 서비스
    - 각각은 microservice일 수도 있고, cronjob일 수도 있고, 분산 시스템 컴포넌트 일 수도 있음
        - 예시) billing service
- 알림 시스템(notification system)
    - 서비스 1~N에 알림 전송을 위한 API를 제공해야 함
    - 제 3자 서비스에 전달할 알림 payload를 만들어낼 수 있어야 함
    - 일단은 한 개의 알림 시스템으로 구성
- 제 3자 서비스(third party services)
    - 사용자에게 실제로 알림을 전달하는 역할
    - 써드 파티를 사용할 때의 유의할 점은 확장성(extensibility)임
        - 추상화를 잘 해야 한다는 거겠지?
    - 어떤 써드 파티는 특정 시장에서 사용할 수 없을 수 있음
- 사용자는 자기 단말에서 알림을 수신해야 함

### 문제점

- **SPOF**: 현재는 알림 시스템이 하나밖에 없고, 그것이 전체 서비스의 장애로 이어질 수 있음
- **규모 확장성**: 한 대의 서비스로 푸시 알림에 관계된 모든 것을 처리하므로, 데이터베이스나 캐시 등 중요 컴포넌트의 규모를 개별적으로 늘릴 방법이 없음
- **성능 병목**: 알림을 처리하고 보내는 것은 자원을 많이 필요로 하는 작업일 수 있음

## 개선

- 데이터베이스와 캐시를 알림 시스템의 주 서버에서 분리
    - 알림 서버를 stateless하게 만들기 위해서
- 알림 서버를 증설하고 자동으로 수평적 규모 확장이 이루어질 수 있도록 설계
    - 알림 서버가 stateless 해졌으니 scale out이 쉬워졌음
- 메시지 큐를 이용해 시스템 컴포넌트 사이의 강한 결합을 끊기
    - 알림 서버는 worker server의 응답을 기다릴 필요가 없음

## 아키텍처

<img width="1170" height="731" alt="image 1" src="https://github.com/user-attachments/assets/873c5ec3-785c-4e45-b92c-9aee02e3e3f3" />


- 서비스 1~N
    - 알림 서버의 API를 통해 알림을 전송
- 알림 서버
    - 알림 전송 API 제공: 스팸 방지를 위해 보통 사내 서비스 또는 인증된 클라이언트만 이용 가능
    - 알림 검증: 이메일 주소, 전화번호 등에 대한 기본적 검증을 수행
    - 데이터베이스 또는 캐시 질의: 알림에 포함시킬 데이터를 가져오는 기능
    - 알림 전송: 알림 데이터를 메시지 큐에 삽입
- 캐시
    - 사용자 정보, 단말 정보, 알림 템플릿 등을 캐시
- 데이터베이스
    - 사용자, 알림, 설정 등 다양한 정보를 저장
- 메시지 큐
    - 시스템 컴포넌트 간 의존성 제거를 위해 사용 + 버퍼의 역할
- 작업 서버
    - 메시지 큐에서 전송할 알림을 꺼내서 제 3자 서비스로 전달하는 역할

### 작업 순서

1. API를 호출하여 알림 서버로 알림 전송
2. 알림 서버는 사용자 정보, 단말 토큰, 알림 설정 같은 메타데이터를 캐시나 데이터베이스에서 가져옴
3. 알림 서버는 전송할 알림에 맞는 이벤트를 만들어 해당 이벤트를 위한 큐에 삽입
4. 작업 서버는 메시지 큐에서 알림 이벤트를 소비
5. 작업 서버는 알림을 제 3자 서비스로 전송
6. 제 3자 서비스는 사용자 단말로 알림 전송

# 상세 설계

## 안정성

- 분산 환경에서 운영될 알림 시스템을 설계할 때는 안정성을 확보하기 위한 사항 몇 가지를 반드시 고려해야 함

### 데이터 손실 방지

- 알림이 지연되거나 순서가 틀려도 괜찮지만 어떠한 상황에서도 알림이 소실되면 안됨
- 그렇기 때문에 알림 데이터를 DB에 보관하고 재시도 메커니즘을 구현해야 함
    - 알림 로그 DB를 유지하는 것이 한 가지 방법

### 알림 중복 전송 방지

- 같은 알림이 여러 번 반복되는 것을 완전히 막는 것은 불가능
- 가끔씩 같은 알림이 중복되어 전송되는데, 그 빈도를 줄이기 위해서 중복 탐지 메커니즘을 도입하고, 오류를 신중하게 처리해야 함
- 보내야 할 알림이 도착하면 그 이벤트 ID를 검사하여 이전에 본 적이 있는 이벤트인지 살피기
    - 중복된 이벤트라면 버리고
    - 그렇지 않으면 알림을 발송

## 추가로 필요한 컴포넌트 및 고려사항

### 알림 템플릿

- 알림 메시지 형식은 대부분 비슷하기 때문에 parameter나 tracking link만 조정하여 지정한 형식에 맞춰 알림을 만들어내는 틀
- 템플릿을 사용하면 알림들의 형식을 일관성 있게 유지할 수 있고, 오류 가능성뿐 아니라 알림 작성에 뜨는 시간도 줄일 수 있음

### 알림 설정

- 사용자가 알림 설정을 상세히 조정할 수 있는 필드
- 알림을 보내기 전에 반드시 해당 사용자가 해당 알림을 켜 두었는지 확인

### 전송률 제한

- 한 사용자가 받을 수 있는 알림의 빈도를 제한
- 사용자에게 너무 많은 알림을 보내면 사용자가 알림을 끌 수 있기 때문ㅇ

### 재시도 방법

- 써드 파티에서 알림 전송에 실패하면, 해당 알림을 재시도 전용 큐에 삽입
- 같은 문제가 반복해서 발생한다면 개발자에게 보고

### 푸시 알림과 보안

- iOS와 android는 appKey와 appSecret을 사용하여 보안 유지
- 인증되거나 승인된 클라이언트만 API를 사용해 알림을 보낼 수 있음

### 큐 모니터링

- 큐에 쌓인 알림의 수는 알림 시스템을 모니터링 할 때 중요한 메트릭임
- 큐에 쌓인 알림의 수가 너무 크면 작업 서버들이 이벤트를 빠르게 처리하지 못한다는 것을 의미

### 이벤트 추적

- 알림 확인율, 클릭율, 실제 앱 사용으로 이어지는 비율 같은 메트릭은 사용자를 이해하는데 중요
- 데이터 분석에는 보통 이벤트 추적 기능도 함께 제공
