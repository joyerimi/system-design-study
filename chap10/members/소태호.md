# 알림 시스템 설계

알림 시스템은 인기 있는 기능입니다.
최신 뉴스, 제품 업데이트, 이벤트 등 고객에게 중요할만한 정보를 **비동기적**으로 제공합니다.

알림 시스템은 크게 모바일 푸시 알림, SMS 메세지, 이메일 3가지로 분류할 수 있습니다.

## 1단계 : 문제 이해 및 범위 설정

늘 있는 방식으로 시작합니다.

- 푸시 알림, SMS 메세지, 이메일 지원 필요
- 연성 실시간(soft real-time) 시스템이라고 가정.
    - 가능한 빠르게 전달되어야 하지만 높은 부하가 걸렸을 땐 약간의 지연 가능
- iOS, android, 데스크탑 지원 필요
- 클라이언트 애플리케이션 프로그램이 보내거나 서버 측 스케줄링을 통해 보낼 수 있음
- 알림 수신하지 않기 기능 필요
- 하루동안 천만 건의 모바일 푸시 알림, 백만 건의 SMS 메세지, 5백만 건의 이메일

## 2단계 : 개략적 설계안 제시 및 동의 구하기

iOS 푸시 알림, 안드로이드 푸시 알림, SMS, 이메일을 지원하는 알림 시스템의 개략적 설계를 먼저 해보겠습니다.
다음과 같은 내용을 다룰 것입니다.
- 알림 유형별 지원 방안
- 연락처 정보 수집 절차
- 알림 전송 및 수신 절차

### 알림 유형별 지원 방향

#### iOS 푸시 알림
iOS에서 푸시 알림을 보내기 위해서는 3가지 컴포넌트가 필요합니다.

<img width="552" height="133" alt="Image" src="https://github.com/user-attachments/assets/a1cdd957-7d2e-4f40-b384-09f15c47d651" />

- 알림 제공자 : 알림 요청을 만들어 애플 푸시 알림 서비스(APNS)로 보내는 주체
    - 알림 요청을 만들기 위해서는 2가지 요소가 필요하다.
        - 단말 토큰(device token) : 알림 요청을 보내는 데 필요한 고유 식별자
        - 페이로드(payload) : 알림 내용을 담은 JSON 딕셔너리다.
    -  <img width="651" height="313" alt="Image" src="https://github.com/user-attachments/assets/1ed03e92-048b-4c1b-9e95-1fca6249b23f" />
-   APNS : 애플이 제공하는 원격 서비스. 푸시 알림을 iOS 장치로 보내는 역할을 담당한다.
- iOS 단말 : 푸시 알림을 수신하는 사용자 단말

#### 안드로이드 푸시 알림
안드로이드 푸시 알림도 비슷한 절차로 전송됩니다. 다만 APNS 대신 FCM(Firebase Cloud Messaging)을 사용합니다.

SMS 메세지를 보내는 경우 트윌리오, 넥스모같은 제3 사업자의 서비스를 이용합니다.

#### 이메일

센드그리드, 메일침프 등을 사용합니다. 전송 성공률도 높고, 데이터 분석 서비스도 제공합니다.

### 연락처 정보 수집 절차
알림을 보내기 위해서 모바일 단말 토큰, 전화번호, 이메일 주소 등의 정보가 필요합니다.
사용자가 앱을 설치하거나 처음 계정을 등록하면 API 서버는 해당 사용자의 정보를 수집하여 데이터베이스에 저장합니다.  
데이터베이스에서 사용할 테이블은 다음과 같습니다.

| 컬럼명            | 타입      |
| -------------- |---------| 
| `user_id`      | BIGINT  |
| `email`        | VARCHAR(255) | 
| `country_code` | INTEGER |
| `phone_number` | INTEGER |
| `created_at`   | TIMESTAMP | 


| 컬럼명                 | 타입           | 
| ------------------- |--------------| 
| `id`                | BIGINT       |
| `device_token`      | VARCHAR(255) | 
| `user_id`           | BIGINT        |
| `last_logged_in_at` | TIMESTAMP    | 


### 알림 전송 및 수신 절차

#### 개략적 설계안

<img width="812" height="594" alt="Image" src="https://github.com/user-attachments/assets/23929c00-e65a-491f-9f4b-a08e100c160c" />

- **1부터 N까지의 서비스** : 서비스 각각은 마이크로서비스이거나 크론잡이거나 분산 시스템 컴포넌트 일 수도 있다.
  사용자에게 납기일을 알리고자 하는 과금 서비스, 배송 알림을 보내려는 쇼핑몰 웹사이트 등이 그 예시다.
- **알림 시스템** : 알림 시스템은 알림 전송/수신 처리의 핵심이다. 1개 서버만 사용한다고 가정하면
  이 시스템은 서버 1 ~ N에 알림 전송을 위한 API를 제공해야 하고, 제3자 서비스에 전달할 알림 페이로드를 만들어 낼 수 있어야 한다.
- 제3자 서비스 : 이 서비스들은 사용자에게 알림을 실제로 전달하는 역할을 한다. 제3자 서비스와 통합할 때 주의할 점은
  확장성이다. 쉽게 새로운 서비스를 추가하거나 기존 서비스를 제거할 수 있어야 한다.
  또 하나 고려할 점은 서비스의 사용 가능 여부이다. 가령 중국에서는 FCM을 사용 불가능하니 대체할 서비스를 찾아야 한다.
- iOS, Android, SMS, 이메일 단말 : 사용자는 자기 단말에서 알림을 수신한다.

하지만 이 설계에는 몇 가지 문제가 있습니다.

- SPOF : 알림 서비스에 서버가 하나밖에 없다는 것은, 서버에 장애가 발생하면 전체 서비스의 장애로 이어진다.
- 규모 확장성 : 한 대 서비스로 푸시 알림에 관계된 모든 것을 처리하므로, 데이터베이스나 캐시 등 중요 컴포넌트의 규모를 개별적으로 늘리기 어렵다.
- 성능 병목 : 알림을 처리하고 보내는 것은 자원을 많이 필요로 할 수 있다.
  예를 들어 HTML 페이지를 만들고 제3자 서비스의 응답을 기다리는 일은 시간이 많이 걸릴 가능성이 있는 작업이다.
  따라서 모든 것을 한 서버에서 처리하면 트래픽이 몰리는 시간에는 과부하 상태가 될 수 있다.

#### 개선해봅시다

<img width="936" height="601" alt="Image" src="https://github.com/user-attachments/assets/2686ee6b-8aac-42a2-ae9c-59dcb2521e35" />

- 먼저 데이터베이스와 캐시를 알림 시스템의 주 서버에서 분리한다.
- 알림 서버를 증설하고 수평적 규모 확장이 이뤄지도록 한다.
- 메시지 큐를 이용해 시스템 컴포넌트 사이의 강한 결합을 끊는다.

알림 서버에서는 다음의 기능을 제공합니다.
- 알림 전송 API : 스팸 방지를 위해 사내 서비스 또는 인증된 클라이언트만 이용 가능하다.
- 알림 검증 : 이메일 주소, 전화번호 등에 대한 기본적 검증을 수행한다.
- 데이터베이스 또는 캐시 질의 : 알림에 포함시킬 데이터를 가져오는 기능이다.
- 알림 전송 : 알림 데이터를 메시지 큐에 넣는다. 하나 이상의 메세지 큐 사용 시 병렬적으로 처리 가능하다.

- 이메일 형태의 알림을 보낼 땐 다음과 같은 JSON으로 요청이 가능합니다.
```json
  {
  "to": [
    {
      "user_id": 123456
    }
  ],
  "from": {
    "email": "from_address@example.com"
  },
  "subject": "Hello, World!",
  "content": [
    {
      "type": "text/plain",
      "value": "Hello, World!"
    }
  ]
}
```

- 캐시 : 사용자 정보, 단말 정보, 알림 템플릿 등을 캐시한다.
- 메시지 큐 : 시스템 컴포넌트 간 의존성을 제거하기 위해 사용한다. 다량의 알림이 전송되어야 하는 경우 버퍼 역할도 가능하다.
  본 설계안에서는 알림의 종류별로 별도 메시지 큐를 사용한다. 다양한 제3자 서비스 중 하나가 고장나도 다른 종류의 알림은 정상 작동 가능하다.
- 작업 서버 : 메시지 큐에서 전송할 알림을 꺼내서 제3자 서비스로 전달하는 역할을 담당하는 서버

해당 서버가 동작 시에는 데이터베이스에서 사용자 정보, 알림 설정 같은 메타데이터를 캐시나 데이터베이스에서 가져옵니다.
알림 서버는 전송할 알림에 맞는 이벤트를 만들어서 해당 이벤트를 위한 큐에 넣습니다.

## 3단계 : 상세 설계

### 안정성
분산 환경에서는 빠질 수 없는 고려사항입니다.

#### 데이터 손실 방지
알림 전송 시스템의 중요한 요구사항 중 하나는 알림이 소실되면 안된다는 것입니다.
알림이 지연되거나 순서가 틀려도 괜찮지만 사라지는 것은 좀 곤란합니다.
이 요구사항을 만족하기 위해서는 알림 데이터를 DB에 보관하고 **재시도 메커니즘**을 구현해야 합니다.

<img width="613" height="352" alt="Image" src="https://github.com/user-attachments/assets/45c1f983-59f8-4385-8fed-e9db44232d13" />

그림은 알림 로그를 DB에 유지시키며 재시도를 위한 데이터를 저장합니다.
재시도의 경우 제3자 서비스가 전송에 실패하면 해당 알림을 재시도 전용 큐에 넣습니다.
같은 문제가 발생한다면 개발자에게 통지해야 합니다.

#### 알림 중복 전송 방지
같은 알림이 여러 번 반복되는 것을 완전히 막기는 어렵습니다.
해결할 수 있는 방법 중 하나는 보내야 할 알림이 도착하면 그 이벤트 ID를 검사하여 이전에 보낸 적 있는지 확인합니다.

> 중복 전송을 100% 방지할 수 없는 이유 : 끝나고 설명

### 추가로 필요한 컴포넌트 및 고려사항

지금까지 연락처 정보 수집과 송수신 과정에 대해 알아봤습니다.
하지만 어림없습니다. 사실 더 많은 컴포넌트가 필요하고 훨씬 복잡합니다.
추가로 고려해볼만한 컴포넌트들에 대해 알아보겠습니다.

#### 알림 템플릿
대형 알림 시스템은 하루에 수백만 건 이상의 알림을 처리합니다.
이 때 알림 메시지의 형식은 비슷한데 일치하는 부분은 템플릿을 활용하여 생성하면 전체를 만들 필요가 없습니다.

#### 알림 설정
알림 설정을 통해 알림을 받고 싶지 않은 사용자는 알림 기능을 끌 수 있습니다.
이 정보는 알림 설정 테이블에 보관할 수 있습니다.

#### 전송률 제한
사용자에게 너무 많은 알림이 가지 않게 제한하는 기능을 고려해볼 수 있습니다.
잦은 알림은 사용자가 알림 기능을 꺼버리게 할 수 있습니다.

#### 푸시 알림과 보안
iOS와 Android의 경우 알림 전송 API는 appKey와 appSecret을 사용하여 보안을 유지합니다.
따라서 인증된, 혹은 승인된 클라이언트만 해당 API를 사용하여 알림을 보낼 수 있습니다.

#### 큐 모니터링
알림 시스템을 모니터링 할 때 중요한 메트릭 하나는 큐에 쌓인 알림의 개수입니다.
이 수가 너무 크면 작업 서버들이 이벤트를 빠르게 처리하지 못한다는 뜻이므로 작업 서버를 증설해야 합니다.

#### 이벤트 추적
알림 확인율, 클릭율같은 메트릭은 사용자를 이해하는 데 중요합니다.
해당 데이터의 분석을 통해 서비스의 개선사항을 파악할 수 있습니다.

## 4단계 : 마무리

알림은 중요 정보를 계속해서 알려준다는 점에서 필요불가결한 기능입니다.


## 중복 전송을 100% 방지할 수 없는 이유

[책의 참고자료 링크](https://bravenewgeek.com/you-cannot-have-exactly-once-delivery/)

일단 해당 링크에서 설명하는 맥락은 다음과 같습니다.

### 분산 시스템을 구현할 때 정확히 한 번(Exactly-Once) 전달할 수 없다.
책에서 자주 얘기했던 내용으로부터 시작해보겠습니다.
네트워크 장애, 데이터 유실 혹은 서버 장애같이 의도치않은 상황으로 인해 통신이 성사되지 않을 수 있습니다.
이를 해결하기 위해 웹의 흐름을 구성하는 컴포넌트를 분산하고 장애 상황에 대응할 수 있는 방법들을 배우고 있는 중입니다.

**분산 시스템에서 정확히 한 번(Exactly-Once) 메세지 전달이 불가능하다는 것은** 바로 이런 개발자가 대처할 수 없는
장애 상황이 발생하기 때문입니다.
해당 게시글에서는 메세지를 전달하는 방법 3가지를 얘기합니다. At-Most-Once, At-Least-Once, Exactly-Once입니다.

| 전달 보장 방식          | 설명                              | 장점        | 단점                           | 적용 사례     |
| ----------------- | ------------------------------- | --------- | ---------------------------- | --------- |
| **At-Most-Once**  | 메세지를 한 번만 보내고 ACK 안 기다림.        | 빠름, 중복 없음 | 메세지 유실 가능                    | 로그, 모니터링  |
| **At-Least-Once** | ACK 없으면 재전송 → 적어도 한 번은 반드시 전달됨. | 메세지 유실 없음 | 중복 처리 가능성 → 멱등성 필요           | 결제, 주문 처리 |
| **Exactly-Once**  | 이론상 불가능 (네트워크/프로세스 장애 때문에)      | 없음        | 구현 불가 (실제는 멱등성 + dedup으로 흉내) | 광고 과금, 회계 |

하지만 본문에서 설명한 알림 시스템은 기능에 따라서 사용자에게 반드시 알림이 가야하는 경우가 있습니다.
즉 최대 한 번 보장(At-Most-Once)의 경우에는 이런 상황에 올바르지 않은 선택입니다.
1번만 보내는데 장애 발생으로 통신하지 못하면 영영 해결할 수 있는 방법이 없게 됩니다.

최소 한 번 전달(At-Least-Once)의 경우 사용자로부터 알림을 수신했다는 ACK를 받을 때까지는 계속 보내겠다는 의미입니다.
즉 사용자에게 중복 알림이 뜰 수 있는 문제점이 발생하게 됩니다.

정확히 한 번(Exactly-Once)의 경우는 단 1번만 보내면서 무조건 사용자가 수신할 수 있게끔 한다는 이야기입니다.
하지만 언제 발생할 지 모르는 장애 상황으로 인해 사실상 **정확히 한 번**은 보장할 수 없다는 의견입니다.

여러 메세지 큐 시스템에서 선전하는 정확한 한 번(Exactly-Once)는 사실상 마케팅에 사용되는 용어이고,
속임수를 사용하여 정확한 한 번처럼 보이게 한다는겁니다.

최소 한 번 전달 방식을 사용하면서
- 메세지 연산을 멱등(idempotent)하게 설계하거나
- 중복을 제거하거나
- 순서가 필요없는 설계

같은 방법을 써서 중복되는 메세지를 여러 개 보내지만 사용자 입장에서는 마치 정확히 한 번 메세지를 보내는 것처럼 보이게 하는겁니다.

예를 들자면, 사용자 기기에 메세지 ID를 저장하는 테이블을 마련하고 알림 메세지가 왔을 때 메세지 ID 테이블을 조회하여
처음 들어온 알림이면 푸시 알림을 보여주고, 이미 보여줬던 알림이면 보여주지 않는겁니다.
즉 중복 전송을 하지만 사용자 기기에 메세지 ID를 기억시켜 중복을 제거하는 전략입니다.  
사용자 입장에서는 알림을 중복 전송을 느끼지 못하고 1번만 알림이 뜬다고 느끼게 하는 것입니다.

### 멱등성 설계
이러한 연산을 할 때 멱등성을 고려하여 설계하면 중복 전송에 대처하기 쉬워집니다.

계좌 잔고를 업데이트할 때 `balance -= 100`을 사용하기 보다 `balance = original_balance - 100`같은 방식을 사용합니다.
감이 좀 잡히시나요? 데이터를 보낼 때 balance만 보내는 것이 아니라 original_balance를 같이 보내 몇 번의 연산을 해도
동일한 결과가 반영되게끔 유도하는 것입니다.
예시 자체는 간단하게 설명하려 했지만 제 생각에는 아마 멱등성을 고려하는 일은 많이 어렵지 않을까 생각합니다.

혹은 upsert 쿼리를 사용하는 것도 한 가지 방법이 될 수 있습니다.

```sql
INSERT INTO orders (id, status)
VALUES (123, 'done')
ON DUPLICATE KEY UPDATE status = 'done';
```
`id = 123`이 없다면 INSERT, 있다면 상태를 'done'으로 UPDATE하도록 쿼리를 작성하는 것입니다.

할 수 있대서 읽어봤는데 위에서 설명한 내용과 동일합니다.
멱등성을 보장하도록 설계한다면 Exactly-Once 방식을 기술적으로 구현한 것 아니냐는 맥락의 글이었습니다.

[Kafka에서는 어떻게 해결을 할까?](https://www.confluent.io/blog/exactly-once-semantics-are-possible-heres-how-apache-kafka-does-it/)

하지만 맥락 자체는 위에서 설명한 내용과 같습니다. Kafka에서 사용하는 연산에 멱등성을 지원하게 하고, 트랜잭션 API를 통해서
원자적(Atomic)하게 동작하는 것을 구현했다고 합니다.

마지막으로 두 줄로 정리하자면 이렇게 정리 가능한 것 같습니다.

1. 정확히 한 번(Exactly-Once)는 이론상 불가능하지만, 중복 전송 + 최소 한 번(At-Least-Once) + 멱등성 설계를 통해 마치 정확히 한 번 전달되는 것처럼 보이게 할 수 있다.
2. 동기적, 보장된 동작을 기대하지 말고, 실패와 비동기성에 대비해 설계하라.
