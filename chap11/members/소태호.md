# 뉴스 피드 시스템 설계

### 뉴스 피드란??
페이스북 설명에 따르면, 홈페이지 중앙에 지속적으로 업데이트되는 스토리들로, 사용자 상태 정보 업데이트,
사진, 비디오, 링크, 앱 활동, 팔로우하는 사람들, 페이지, 그룹으로부터 나오는 좋아요 등
앱에서 나올 수 있는 모든 정보들이 보여지는 화면입니다.

## 1단계 : 문제 이해 및 설계 범위 확정
뉴스 피드 시스템을 설계할 때 알아야 할 것은 어떤 기능을 지원할 지 파악하는 것이 중요합니다.
책에 있는 가상 면접으로부터 도출 가능한 기능은 다음과 같습니다.

- 모바일 앱과 웹 모두 지원해야 한다.
- 뉴스 피드 페이지에 새로운 스토리를 올릴 수 있어야 하고, 친구들이 올리는 스토리를 볼 수 있어야 한다.
- 뉴스 피드의 순서는 시간 흐름 역순으로 보여진다.
- 한 명의 사용자는 최대 5000명의 친구를 가질 수 있다.
- 트래픽 규모는 매일 천만 명 방문(10million DAU)
- 스토리에는 이미지나 비디오 등의 미디어 파일이 포함될 수 있다.

> 최대 5000명의 친구를 가질 수 있다면, 조회 시 5000명 분의 스토리를 가져오지 않게 해야겠군요.(당연한 얘기)

## 2단계 개략적 설계안 제시 및 동의 구하기

설계안은 `피드 발행`과 `뉴스 피드 생성` 두가지 부분으로 나누어 보겠습니다.
- 피드 발행 : 사용자가 스토리를 포스팅하면 해당 데이터를 캐시와 DB에 기록한다. 새 포스팅은 친구의 뉴스 피드에도 전송된다.
- 뉴스 피드 생성 : 지면 관계상 뉴스 피드는 모든 친구의 포스팅을 시간 흐름 역순으로 모아서 만든다고 가정한다.

### 뉴스 피드 API
뉴스 피드 API는 클라이언트와 서버가 통신하기 위해 사용하는 수단입니다.

#### 피드 발행 API
새 스토리를 포스팅하기 위한 API입니다. POST 형태로 요청합니다. 스펙은 다음과 같습니다.
- POST /v1/me/feed
  - 인자
    - 바디 : 포스팅 내용
    - Authorization : API 호출을 인증하기 위해 사용

#### 피드 읽기 API
뉴스 피드를 가져오는 API입니다. 스펙은 다음과 같습니다.
- GET /v1/me/feed
  - 인자
    - Authorization : API 호출을 인증하기 위해 사용

### 피드 발행
피드 발행 시스템의 개략적 형태는 다음과 같습니다.

<img width="534" height="767" alt="Image" src="https://github.com/user-attachments/assets/e3b146c1-f45f-4863-a107-0961c0197a2c" />

- 사용자 : 모바일 앱이나 브라우저에서 새 포스팅을 올리는 주체
- 로드 밸런서 : 트래픽을 웹 서버들로 분산
- 웹 서버 : HTTP 요청을 내부 서비스로 중계하는 역할
- 포스팅 저장 서비스 : 새 포스팅을 DB와 캐시에 저장
- 포스팅 전송 서비스 : 새 포스팅을 친구의 뉴스 피드에 푸시한다. 뉴스 피드 데이터는 캐시에 보관하여 빠르게 읽어갈 수 있도록 한다.
- 알림 서비스 : 친구들에게 새 포스팅이 올라왔음을 알리거나, 푸시 알림을 보내는 역할 담당

#### 뉴스 피드 생성
뉴스 피드 생성의 구조도 발행과 큰 차이는 없습니다.

<img width="395" height="619" alt="Image" src="https://github.com/user-attachments/assets/ab9e9fc0-890a-460d-bf53-47ff77ee7ce2" />

사용자가 요청을 보내고 로드밸런서가 트래픽을 분산, 서비스는 캐시에서 뉴스 피드를 가져온다.
차이가 있다면 DB는 따로 없고, 뉴스 피드 캐시에서 렌더링할 뉴스 피드의 피드 ID를 보관한다는 점입니다.

## 3단계 : 상세 설계

### 피드 발행 흐름 상세 설계

<img width="748" height="929" alt="Image" src="https://github.com/user-attachments/assets/465347df-04a3-4b7d-98e4-dbaaa1a65f2d" />

상세한 설계를 담은 이미지입니다. 해당 절에서는 따로 설명하지 않은 인증 및 rate limit과 관련된 내용들이 있습니다.

#### 웹 서버
클라이언트와 통신뿐만 아니라 인증이나 처리율 제한 등의 기능도 수행합니다.

#### 포스팅 전송(팬아웃) 서비스
포스팅 전송, 팬아웃(fanout)은 어떤 사용자의 새 포스팅을 그 사용자와 친구 관계에 있는 모든 사용자에게 전달하는 과정입니다.
팬아웃 모델에는 2가지가 있습니다.
1. 쓰기 시점에 팬아웃하는 모델(push 모델)
    - 새로운 포스팅을 기록하는 시점에 뉴스 피드를 갱신하게 된다. 포스팅이 완료되면 바로 해당 사용자의 캐시에 해당 포스팅을 기록합니다.
    - 장점 
      - 뉴스 피드가 실시간으로 갱신되며 친구 목록에 있는 사용자에게 즉시 전송
      - 새 포스팅이 기록되는 순간 뉴스 피드가 갱신되므로 뉴스 피드를 읽는 데 드는 시간이 비교적 짧다.
    - 단점
      - 친구가 많은 사용자의 경우 친구 목록을 가져오고 그 목록에 있는 사용자 모두의 뉴스 피드를 갱신하는 데 많은 시간이 소요될 수 있다.(hotkey 문제)
      - 서비스를 자주 이용하지 않는 사용자의 피드까지 갱신해야 하므로 컴퓨팅 자원이 낭비된다. 
2. 읽기 시점에 팬아웃하는 모델(pull 모델)
    - 피드를 읽어야 하는 시점에 뉴스 피드를 갱신한다. 따라서 요청 기반(on-demand)모델이다.
    - 장점
      - 비활성화된 사용자나 거의 로그인하지 않는 사용자가 많은 경우 이 모델이 유리하다. 로그인하기전까지 컴퓨팅 자원을 소모하지 않기 때문이다.
      - 데이터를 친구 각각에 푸시하는 작업이 필요없어 핫키 문제가 발생하지 않는다.
    - 단점
      - 뉴스 피드를 읽는 데 많은 시간이 소요될 수 있다.

저희는 2가지 방법 모두 사용하여 장점만 취하는 전략을 취하겠습니다.  
뉴스 피드를 빠르게 가져올 수 있도록 하는 것은 아주 중요하므로 대부분의 사용자에 대해서는 푸시 모델을 사용합니다.
친구나 팔로어가 많은 사용자의 경우에는 팔로어로 하여금 해당 사용자의 포스팅을 필요할 때 가져가는 풀 모델을 사용하여 과부하를 방지할 것입니다.
마지막으로 안정 해시를 통해 요청과 데이터를 고르게 분산하여 핫키 문제를 줄일 수 있습니다.

팬아웃 서비스에 대해 자세히 알아보겠습니다.

<img width="508" height="541" alt="Image" src="https://github.com/user-attachments/assets/8ef1db5a-95ce-4c77-afca-938a6b8549a5" />

1. 그래프 데이터베이스에서 친구 ID 목록을 가져온다.
2. 사용자 정보 캐시에서 친구들의 정보를 가져온다.
3. 친구 목록과 새 스토리의 포스팅 ID를 메시지 큐에 넣는다.
4. 팬아웃 작업 서버가 메시지 큐에서 데이터를 꺼내어 뉴스 피드 데이터를 뉴스 피드 캐시에 넣는다.
    뉴스 피드 캐시에는 <포스팅 ID, 사용자 ID>만 저장하여 메모리 요구량은 낮춘다.
    메모리 크기를 적정 수준으로 유지하기 위해 캐시의 크기에 제한을 두며, 해당 값은 조절 가능하도록 한다.
    뉴스 피드에 올라온 모든 스토리를 볼 확률은 지극히 낮고 대부분 최신 스토리를 보려 하므로 캐시 미스가 날 확률은 낮다.

#### 피드 읽기 흐름 상세 설계

<img width="647" height="626" alt="Image" src="https://github.com/user-attachments/assets/ac1c2668-c67d-422b-9139-d03e3ec439c8" />

일단 이미지나 비디오같은 미디어 콘텐츠는 CDN에 저장하여 빨리 읽어갈 수 있도록 했습니다.

1. 사용자가 뉴스 피드를 읽으려는 요청을 보낸다.
2. 로드 밸런서가 요청을 웹 서버 중 하나로 보낸다.
3. 웹 서버는 피드를 가져오기 위해 뉴스 피드 서비스를 호출한다.
4. 뉴스 피드 서비스는 뉴스 피드 캐시에서 포스팅 ID 목록을 가져온다.
5. 뉴스 피드에 표시할 사용자 정보, 포스팅 정보를 사용자 캐시와 포스팅 캐시에서 가져와 완전한 뉴스 피드 형태로 만든다.
6. 생성된 뉴스 피드를 JSON 형태로 클라이언트에게 보낸다.

#### 캐시 구조
캐시는 뉴스 피드 시스템의 핵심 컴포넌트입니다. 본 설계안의 경우 캐시를 다섯 계층으로 나눕니다.

<img width="527" height="286" alt="Image" src="https://github.com/user-attachments/assets/2635ba93-1e32-4ac2-bcef-0d4340abd769" />

뉴스 피드 : 뉴스 피드 ID 보관
콘텐츠 : 포스팅 데이터를 보관한다. 인기 콘텐츠는 따로 보관한다.
소셜 그래프 : 사용자 간 관계 정보를 보관한다.
행동 : 포스팅에 대한 사용자의 행위에 관한 정보를 보관한다. 포스팅에 대한 '좋아요', '답글' 등 해당된다.
횟수 : '좋아요'횟수, 응답 수, 팔로어 수, 팔로잉 수 등의 정보를 보관한다.

## 4단계 마무리
다른 설계 문제와 마찬가지로 정답은 없습니다. 요구사항 분석을 철저히 하고 적절한 기술을 사용할 수 있어야 합니다.
회사마다 독특한 제약이나 요구조건이 있으므로 기술 선택 시 배경을 고려하고 어떤 타협적 결정들이 있었는지 이해하고 설명할 수 있어야 합니다.
시간이 남는다면 다음과 같은 내용도 논의해볼만 합니다.

DB 규모 확장
- 수직적 vs 수평적
- SQL vs noSQL
- master-slave 다중화
- replica에 대한 읽기 연산
- 일관성 모델
- DB 샤딩

그 외 주제
- 웹 계층을 무상태로 운영
- 가능한 한 많은 데이터를 캐시할 방법
- 여러 데이터 센터를 지원할 방법
- 메시지 큐를 사용하여 컴포넌트 간 결합도 낮추기
- 핵심 메트릭에 대한 모니터링
